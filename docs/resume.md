## 1. 简历项目描述

### 1.1 标准版（3 行，AI 应用 / Agent 开发岗）

> **AutoSkill：面向 Agent 的自进化技能生成与热加载系统**（个人开源项目）
> - 设计并实现 Agent 动态技能生产线：技能池未覆盖的需求由 LLM 自动生成工具函数，经 AST 白名单、契约检查、沙箱自测四层校验后入库热加载，Agent 无需重启即可调用；含熔断隔离、影子验证、自动回滚的治理闭环
> - 实现"向量召回 + LLM 终审"双路由与五层沙箱纵深（受限命名空间 / PEP 578 审计钩子 / 资源围栏 / Docker 可切换）；HTTP 类技能经 egress 域名白名单四点校验放行
> - 45 条冻结评测集实测：生成成功率 93%、路由正确率 100%、静默失败 0、注入拦截 100%；105 项测试 + CI 全绿；FastAPI / Chroma / DeepSeek，单机一键复现

### 1.2 精简版（空间紧张，2 行）

> **AutoSkill**（开源）：Agent 自进化技能系统——LLM 自动生成工具函数，四层校验入库热加载；向量召回 + LLM 终审路由，熔断-影子验证-自动回滚治理闭环。45 条冻结评测实测生成 93% / 路由 100% / 零静默失败，105 项测试 CI 全绿。

### 1.3 后端岗侧重版（强调隔离与治理）

> **AutoSkill**（开源）：Agent 动态技能生产与治理系统。核心为五层沙箱纵深：AST import 白名单、受限内建命名空间、PEP 578 审计钩子（默认拒绝一切文件/网络/子进程调用，HTTP 经域名白名单四点校验）、内存看门狗 + Job Object、Docker 执行器可切换；技能治理含熔断隔离、影子灰度晋升、自动回退。105 项测试覆盖并发/熔断/重建，CI 全绿。

### 1.4 写法要点

- **不要写**"支持多租户/分布式/高并发"——没做的就是不做，写了必被拆穿
- **不要写**"正确性保证"——写"质量门禁 + 冻结评测集判分"，诚实反而加分
- 百分比必须能当场出示报告（`eval/report.md` 在仓库里，手机可开）

## 2. 分层面试话术

### 2.1 电梯版（30 秒，面试官问"介绍个项目"）

> "普通 Agent 只能调用预定义的工具，我的项目让 Agent 自己生产工具：用户提一个技能池没覆盖的需求，系统用 LLM 生成工具函数，过四层校验——语法、契约、AST 安全白名单、沙箱自测——通过后入库热加载，Agent 下一轮对话直接可用。技能坏了会熔断隔离，同类需求再进来时自动生成修复版本热替换。整条链路用 45 条冻结评测集实测，四项指标全达标，包括零静默失败和注入 100% 拦截。"

### 2.2 深讲版（2 分钟，面试官说"详细讲讲"）

按"问题 → 方案 → 两个取舍 → 数据"展开：

> "**问题**：Agent 落地最大的痛点是工具供给——工具靠人工开发，需求一变就得改代码。
> **方案**：我做了一条技能生产线。路由层先判'要不要生产'：向量召回 top-3 候选，LLM 终审裁决——这个设计是因为实测本地 embedding 对中文改述的相似度只有 0.1~0.3，固定阈值不可靠；LLM 一次调用同时完成命中判断、参数抽取和拒绝理由。未命中就走生成：四层校验（语法、入口契约、AST 白名单、沙箱自测），失败带错误回喂最多修 3 轮，通过后入库热加载。
> **两个关键取舍**：一是热加载不用 importlib——技能本来就跑在独立子进程，每次现起读最新版本天然就是热加载，模块缓存污染问题不存在，回滚退化成版本指针切换；二是测试自测同源问题——实现和测试都是 LLM 生成的，测试通过不等于正确，所以判分只用 45 条人工预写冻结的期望值，和 LLM 生成的测试完全隔离。
> **数据**：45 条冻结评测集，生成成功率 93%、路由正确率 100%、静默失败 0、注入拦截 100%；105 项测试，CI 在 GitHub Actions 全绿。唯一没过的 B 组用例是 LLM 自己的心算错误被门禁正确拒绝——显式失败而不是静默出错，这正是系统设计的行为。"

### 2.3 架构深挖版（5 分钟，面试官追问架构）

在 2.2 基础上按面试官追问方向展开（备好三张图）：
1. **四层架构图**（ARCHITECTURE §1）：接入/调度/核心/存储
2. **全链路时序图**（§2）：一次 ensure 的完整生命周期
3. **技能状态机**（§3）：active ↔ quarantined + 影子晋升 + 自动回退

追加热点（每个 30 秒）：
- 五层沙箱为什么层层冗余（§5，含"eval 无审计事件所以 eval 必须从命名空间移除"的实测细节）
- egress 白名单的四点校验与"操作员拥有出站策略"的信任模型
- 影子灰度：候选版本先用真实需求参数执行，通过才热替换，失败自动回滚
- 跨语言召回：混合部署（chat=DeepSeek / embedding=多语言模型），英文改述召回中文技能 5/5

### 2.4 反问与边界应答

被问到没做的功能（多租户/分布式/前端）：
> "这些在验收文档里明列为非目标。MVP 的边界是有意划的——单机工程可用优先，扩容路线写在架构文档第 6 节：多实例需要把生成锁外置、向量库换服务化部署，方案是清楚的，但当前形态不需要。"

被问到"这项目 AI 写的吧"：
> "AI 辅助了实现，但架构决策、安全模型和验收标准是人定的——比如为什么 egress 违规是终态拒绝、为什么判分只用冻结期望值，这些 trade-off 每一条都能讲出实测依据。评测过程中 AI 生成代码暴露的三个真实缺陷（JSON 截断、假实现绕过注入测试、别名绕过静态检查）都是我发现并修的，修复方式在 git 历史里。"
