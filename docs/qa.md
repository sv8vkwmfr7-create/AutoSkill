# AutoSkill 面试 Q&A（高频问题与参考答案）

> 原则：每个回答先给结论，再给证据（实测数字/代码位置），最后主动暴露边界——答辩时"知道自己不知道"比假装全知更加分。

---

## Q1：这个项目和 Voyager（NeurIPS'23 的 Minecraft 技能库）有什么区别？

**结论：思路同源，工程语境完全不同。** Voyager 验证了"技能库 + 向量检索 + 代码生成"的可行性，本项目把同一思想搬进**服务化的生产-校验-治理闭环**：
1. Voyager 的 skill 在游戏环境里"试了就算学会"，没有独立的校验层；AutoSkill 的每次生成必须过四层校验（语法/契约/AST 白名单/沙箱自测），并有**人工冻结期望值**的批量评测托底
2. Voyager 无服务化概念；AutoSkill 是 HTTP 服务 + CLI 双接入，注册表持久化、重启重建、熔断隔离、版本热替换
3. Voyager 的技能坏了就坏了；AutoSkill 有**熔断 → 同类需求触发 v2 自修复 → 热替换**的治理闭环
4. Voyager 的嵌入模型面向英文游戏文本；本项目在无 GPU、无网络依赖的约束下用本地 bigram-hash + LLM 终审裁决替代纯向量阈值路由
一句话：**Voyager 回答"Agent 能不能学会工具"，AutoSkill 回答"工具生产线怎么工程化"。**

## Q2：成功率 90% 是怎么测出来的？

分三种情况回答：① 实测 ≥90%：出示 `eval/report.md`（35 条冻结评测集：池外 10 条生成、池内 10 条改述、注入 5 条），说明判分口径（错误命中计失败、静默失败单列）；② 实测 85%~90%：报实测值并解释失败条目的归因（生成阶段第几轮失败、失败类型分布——报告里有）；③ 低于 85%：如实说明当前模型/参数下的实测值与瓶颈分析。**禁止报未实测的数字。**

## Q3：单测是 LLM 生成的，测试通过能说明代码正确吗？

不能——这是"单测同源"问题，同一个 LLM 的幻觉可能同时污染实现和测试。所以系统的设计是三层：LLM 自生成的 `tests.json` 只作为**质量门禁**（挡住语法错、运行崩的代码）；正确性由**人工预写、冻结的评测期望值**独立判分（`eval/evalset.json` 与 LLM 生成完全隔离）；评测需求文本内嵌精确规则与边界示例压缩歧义。最终数字里任何"测试全过但结果错"的条目都会被评测如实计入失败。

## Q4：没有 Docker，你的沙箱算安全吗？

local 后端整体仍是 **dev-only 行为隔离**——这是主动声明的边界。但在无 Docker 环境下我做到了用户态可达的纵深防御（五层，`docs/ARCHITECTURE.md` §5）：① AST 静态层（import 白名单 23 模块 + builtin 黑名单 + **别名/dunder 字符串封禁**）；② **受限内建命名空间**——runner 给技能模块注入的 `__builtins__` 里根本没有 eval/exec/open/getattr，引用即 NameError 显式失败（关键原因：CPython 的 builtin eval 不触发审计事件，只能从命名空间层面移除）；③ **PEP 578 审计钩子**默认拒绝文件写入/网络/子进程/越界读取/非白名单 import（含 `_hashlib` 这类传递性标准库依赖的路径判定）；④ **内存看门狗**（50ms 轮询进程树聚合 commit，超 256MB 杀树）+ Job Object + 超时杀树；⑤ **DockerExecutor 已实装**（`--network none --read-only --memory 256m --pids-limit 64`），装 Docker 即切换。可以现场演示：手写一个绕过静态检查的别名攻击 `items=[open]`，运行时被拒；8GB 内存炸弹 0.4 秒被看门狗终止。残余边界如实声明：用户态隔离不防内核攻击向量，真正安全边界在容器层。

## Q5：为什么不用 importlib 做进程内热加载，性能不是更好吗？

因为技能本来就跑在独立子进程里，每次调用 spawn 新进程读最新版本文件，**天然就是热加载**——主进程只需要元数据注册表（指向文件路径），从不 import 技能代码。这消灭了 importlib 方案的三个真实问题：模块缓存与 reload 状态污染、技能异常拖垮主服务、依赖版本冲突。"回滚"简化成把版本指针指回旧目录。代价是每次调用多一次 Python 冷启动（实测 0.15~0.25s），在工具调用场景完全可接受；真要优化，Docker 常驻 warm pool 比进程内 importlib 更干净（列入扩容路线，MVP 非目标）。

## Q6：技能数量到 1000 个，向量召回还撑得住吗？

撑得住但路由策略要升级，方案是四步（架构文档 §6）：生成时强制打标签 → 路由先按标签粗筛（千 → 数十）→ embedding 换 provider 模型（配置即切）→ 高频需求缓存裁决结果（LRU）。另外两个治理点：入库前相似度去重防技能膨胀；新版本影子执行灰度后再替换。MVP 阶段 20~30 个技能实测 top-3 召回 + LLM 裁决的准确率数据在报告里，扩容不推翻架构、只加层。

## Q7：熔断阈值为什么是连续 3 次？

三个理由：① 一次失败可能是调用方参数问题（虽然参数预校验已拦截大部分），两次失败才能区分"偶发"与"持续"；② 阈值过低会导致技能被频繁误隔离，隔离期间该能力不可用，代价大于容忍两次重试；③ 可配置（`AUTOSKILL_BREAKER_THRESHOLD`），3 是 MVP 实测的平衡点。补充设计细节：只有**真实执行失败**计数（协议 ok=false/超时/崩溃），参数预校验失败不计数；隔离触发时同步更新向量库元数据，路由立即排除。

## Q8：用户需求里藏了 prompt injection 怎么办？

需求文本确实会进入生成 Prompt（这是能力，也是攻击面）。防线逐层：① 生成器被明确要求**诚实拒绝**能力边界外的需求（输出 `{"reject": true}`，禁止编造假实现）——评测 C 组 5 条注入需求（抓网页/读文件/执行命令/连库/上传）100% 显式拒绝且不产生新技能；② 生成产物必须过 AST 白名单，诱导出的 `import requests`/`open()`/`eval()` 在静态层被拒绝；③ 就算攻击者构造出绕过静态层的载荷（内建别名、动态属性），运行时的**受限内建命名空间 + PEP 578 审计钩子**会拒绝——`open`/`getattr` 在技能命名空间里不存在，文件写入/网络/子进程系统调用被审计事件拦截；④ 资源层兜底内存炸弹与死循环；⑤ 容器层（DockerExecutor）提供内核级隔离。残余风险如实说明：纯计算白名单内的逻辑性错误结果依赖评测期望值兜底。

## Q9：生成 3 轮自修正还是失败怎么办？

显式报错，绝不静默。失败分级随错误回喂：parse（JSON/语法）→ contract（缺 run 入口）→ guard（白名单违规）→ sandbox（自测失败）。guard 类失败特殊处理：即便 LLM 重试，白名单外的代码永远不会被放行——所以"抓网页/读文件"类需求会在 3 轮后以"能力边界"显式拒绝（实测约 40~80s，报告 C 组）。被拒绝的需求不产生任何技能入库；上层（Agent）收到结构化错误后向用户如实说明。这就是"拒绝也是正确行为"的设计。

## Q10：这和直接用 Function Calling / MCP 有什么关系？

互补而非替代。Function Calling/MCP 定义了"Agent 怎么调用工具"的协议，但工具本身仍需人工开发注册；AutoSkill 补的是供给侧——技能的 `params_schema` 直接编译成 function-calling 的工具定义，MCP server 也可以把本系统的技能池当作后端（`POST /ensure` 即动态注册新工具）。换句话说：协议层标准（MCP/FC）+ 供给层自动化（本项目）= 完整的"自进化 Agent"。

## Q11（追问预备）：为什么路由要花一次额外的 LLM 调用？

因为"错误命中"是最危险的失败模式——静默返回错误结果。纯阈值路由的两个结构性问题：阈值随技能规模漂移、embedding 对中文短句区分度有限（实测本地哈希 embedding 下同义改述相似度仅 0.12~0.32，任何固定阈值都不可靠）。LLM 裁决一次调用（实测约 1s）同时完成命中判断、参数抽取、拒绝理由，且天然给出可解释的路由日志。

## Q12（追问预备）：演示环境是 dev-only，什么时候敢上生产？

三个前置条件：① DockerExecutor 实装并通过**同一套评测脚本**双后端复跑（对比报告本身就是交付物）；② egress 白名单代理上线后，才允许 HTTP 类技能进入场景定位；③ 评测集扩容 + 影子执行灰度。核心观点：生产化的瓶颈不在代码而在**评测基建**——冻结期望值的评测集让每次架构变更都有回归基线，这是本项目最可迁移的工程习惯。
